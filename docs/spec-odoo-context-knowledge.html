Spec · in-Odoo MCP module

Odoo context served from Knowledge

Version 2.1 · 03 Nov 2026 (as built) Owner: Meng Huey Draft for maintainer review

Request. One release of the in-Odoo MCP module that adds two read tools and two write tools. Together they serve QIP's Odoo context (entity profiles, journals, chart of accounts, posting rules) to every finance user through the connector they already use.

  • Content lives in Odoo Knowledge, not in the module. Day-to-day updates are article edits, with no redeploy.
  • Routing is by Odoo company id. One call returns the right entity page, its structure's journals and chart, its rulebook and any warnings.
  • Agents propose, people approve. Agent writes land as proposals; a named reviewer applies them.
  • A further release is only needed if the tools themselves change.

What changed from version 1

  • Four tools instead of six. odoo_context_for now returns the company's resolved journals, replacing resolve_journal. Search and get are merged into odoo_context_lookup. The two write tools stay separate, so proposing and approving carry different behavioural hints and remain distinct steps in the audit trail.
  • Packaging. The tools ship in the existing MCP module. knowledge is added to its depends, and the module README and docs state that it requires Odoo 18 Enterprise with Knowledge.
  • Property definitions. Knowledge applies a property definition to an article's direct children only. Definitions are now set on every parent article, not just the root.
  • Drift facts. Entity articles carry year end, parent and currency as properties, so the drift check compares fields rather than parsing article text.
  • Rejected proposals are kept active under Proposals → Rejected instead of archived, because archived Knowledge articles go to the Trash, which is purged automatically.
  • Proposal rights. Contributors only need read access to the workspace; the propose tool creates the proposal with elevated rights after checking the group.
  • Journal resolution. Bank journals resolve to the company's own bank journal only. The consolidation lookup is limited to the company's ancestor chain, because CJE exists in three companies.
  • Both servers. The independent server gets the same four tools, and a write guard on both servers stops the generic tools editing context articles outside the proposal flow.
  • Company filter. Knowledge has no company field, so the tools only return articles for companies the user is allowed into in Odoo.
  • Behavioural hints for each tool, a default that keeps proposals out of search, and extra acceptance tests for each of the above.

Scope and non-goals

In scope

  • Four new odoo_context_* tools in the existing MCP module (odoo_module_mcp_server), in their own file and registered through register_tool like the generic tools. They follow the existing tool conventions and controls on /mcp/v1.
  • knowledge added to the manifest's depends. The module README and the manifest description state the requirement: Odoo 18 Enterprise with the Knowledge app. QIP's production database already meets it.
  • Two security groups and two settings (workspace root article, stale-after days), shipped as module data.
  • The same four tools, with the same names, inputs, outputs and behavioural hints, on the independent server (odoo-mcp/server.py). See "Independent server parity".
  • A workspace write guard in the existing generic write tools on both servers.
  • A Knowledge workspace convention (article properties) that the tools rely on.
  • A one-off import of the existing context folder into Knowledge. QIP finance runs this through the MCP; no maintainer work.

Not in scope

  • No new models, fields or views. Article metadata uses Knowledge's built-in article properties, so the "no model tampering" control stays on.
  • No change to the OAuth / API-key set-up. The only change to the existing tools is the workspace write guard (see "Access control").
  • No direct agent edits to approved articles. Agents can only create proposals.
  • No sync back to OneDrive or git. A periodic export for audit is a separate, later piece.

Content model

All context sits under one Knowledge workspace article, Finance – Odoo context. One article covers one concept, the same rule as the current folder. The tools find articles by their properties, never by title or position, so people can rename and reorder freely.

Article tree

Article properties

In Knowledge, a property definition applies only to the direct children of the article that holds it. Every article marked "defines properties" above therefore carries the same definition below. The maintainer sets it on the root, the import copies it to each other parent, and a new parent article is set up the same way. The tools treat an article with no ctx_type as invisible, so a missing definition fails safe and the tools report it (see warnings).

Selection options are stored with keys equal to their labels (for example key entity, label entity), so domains filter on stable values.

New MCP tools

The two read tools run as the calling user, with no elevated rights. The two write tools touch only knowledge.article and check the caller's group first. All tools return article bodies converted to markdown, with a link to each article. The conversion runs inside the module and uses only libraries Odoo already ships (lxml), so the provider's host needs no extra Python packages.

Routing in odoo_context_for

This is the core of the request.

  1. Read the company live from res.company: name, parent, root, year end, currency, opening date and lock dates.
  2. Find its structure: the approved article with ctx_type = structure whose ctx_company_id is the company's root.
  3. Resolve the company's journals live (see "Journal resolution" below) and return them in a journals block. This step does not depend on Knowledge, so users without workspace access still get it.
  4. Refuse the call if company_id is not one of the user's allowed companies.
  5. Collect approved articles, filtered by company as described under "Access control": the entity article and rulebook for company_id; the structure's Journals, Chart, Taxes, Banking and Partners articles; and the Read-me-first guide.
  6. Trim by task. For example, elimination drops Taxes and Banking, and bank keeps Banking and the rulebook. No task returns everything.
  7. Drift check: compare year end, parent and currency from step 1 with the entity article's ctx_year_end, ctx_parent_id and ctx_currency. Return any mismatch in warnings with both values. The check never edits the article.
  8. Flag any routed article whose ctx_verified_on is older than the stale-after setting (default 90 days).
  9. Warn when an expected article is missing, including one that has no properties because its parent lacks the definition.

Example. odoo_context_for(67, "elimination") returns Woolwich 1 Elimination's facts (parent 9 B Woolwich Limited, root 6 Straits HoldCo II, year end 31 Jul, GBP), its resolved journals (consolidation: CJE 224, owned by Straits HoldCo II, shared), its entity and rulebook articles, the shc-ii Journals, Chart and Partners articles, and the warning "year end 31 July: a July close is a year-end close".

Journal resolution in odoo_context_for

Computed live from account.journal as the calling user, not from articles. The journals block has one entry each for general, purchase, sale and bank, plus consolidation where one applies. Each entry gives the journal id, code, owning company, shared true/false and the posting procedure, or an error.

  1. Bank: list the company's own active bank journal(s) and nothing else. If it has none, the entry is an error saying so; never fall back to another company's.
  2. General, purchase and sale: use the company's own active journal of that type if it has one (shared: false, post directly). For general, the CJE and EXCH journals are skipped; when several candidates remain (e.g. MISC and HFS at SP6 HoldCo), the lowest-sequence one is returned and the rest are listed as alternatives.
  3. Otherwise walk up the company's ancestors (parent_path), nearest first, to the first one that owns such a journal. Return shared: true with the procedure "create under the owning company, then set company_id while in draft". (Version 2 had a "post directly if an Odoo branch" exception; it is dropped because in Odoo 18 every child company is a branch, and the workaround is what has been observed to work on this instance.)
  4. Consolidation: match only journals coded CJE, and only within the company and its ancestors. CJE exists in three companies today (202 QIP Development Group LLC, 224 Straits HoldCo II, 122 Q.I.P. SP6 UK HoldCo), so an unrestricted match would pick the wrong structure. Omit the entry if no ancestor has one.
  5. If the owning journal belongs to a company the user cannot access, that entry is an error naming the company and asking the user to request access. Do not elevate rights to read it.

Example. odoo_context_for(68) returns a consolidation entry of CJE (224), owned by Straits HoldCo II (6), shared: true.

Update and review flow

Agents and users never edit an approved article directly. Every change goes through a proposal that a reviewer approves.

  • Propose. odoo_context_propose checks the caller is in the contributor group, then creates a child article under Proposals with elevated rights limited to that one create. It sets ctx_status = proposed and ctx_target, and records the proposed text, the evidence and the reason. The record's creator stays the calling user, so Odoo shows who proposed it. Reviewers are notified through the article's chatter.
  • Approve. odoo_context_apply_proposal runs as the reviewer, without elevated rights, so Knowledge's own history shows who made the change. It writes the change into the target article, sets ctx_verified_on to today and ctx_verified_via to the proposal's evidence, appends one row to Change log (date · article · change · proposed by · approved by), and marks the proposal approved.
  • Reject. The proposal is marked rejected with the reviewer's note and moved under Proposals → Rejected. It stays active: it is not archived, because archived articles go to Knowledge's Trash, which is purged automatically. The target is untouched.
  • Edits in the Knowledge UI. People editing in the UI are reviewers by convention and add their own change-log row. The tools do not police UI edits, and the Change log is append-only by convention, not enforced.

Access control and guardrails

  • Reads follow Odoo rights. Both read tools run as the calling user. Anyone who cannot open the workspace in Knowledge gets nothing back. The workspace is shared with the finance team's Odoo users as read-only; no per-article rules are needed today.
  • Knowledge is not company-scoped. knowledge.article has no company field; access is set per article (internal permission and members) and passes down the tree. Anyone who can read the workspace in the Knowledge app can read every entity's article, whichever Odoo companies they are allowed into.
  • Company filter in the tools. On top of Knowledge's own permissions, the read tools only return articles for companies the user is allowed into (env.user.company_ids):
    • Company articles (those with ctx_company_id, such as entity articles and rulebooks) are returned only if that company is one of the user's allowed companies.
    • Structure articles and their children are returned only if the user is allowed into the structure's root company or any company below it.
    • Articles that are not about one company (Read me first, Organisation, FS sections, Reports, Change log) are returned to anyone with workspace access.
    • odoo_context_for for a company the user is not allowed into is refused outright.
    • odoo_context_lookup by article_id for a filtered article returns "not found", the same answer as for an article that does not exist, so the result reveals nothing.
    • odoo_context_propose and odoo_context_apply_proposal are refused when the target article belongs to a company outside the caller's allowed companies.
    This filter applies only through the MCP tools. Anyone opening the Knowledge app directly still sees what the workspace permissions allow, so the workspace must not hold anything that needs stricter control than the data classification below.
  • Two security groups, shipped as module data, never created by agents:
    • Context contributor (finance users): may call odoo_context_propose.
    • Context reviewer (initially Meng Huey and Linus): may call odoo_context_apply_proposal, and has write access to the workspace.
  • Write scope. The propose tool may only create articles under Proposals. The apply tool may only write articles under the workspace root. Any other model, or an article outside the workspace, is refused.
  • Limited elevation. The only elevated-rights operation is the single proposal create, after the group check. Every other call runs as the user.
  • No silent edits. odoo_context_propose never changes an approved article. Only odoo_context_apply_proposal does, and it always writes a change-log entry.
  • Workspace write guard. Without one, a reviewer, who has edit rights on the workspace, could have an agent change an approved article through the generic tools with no proposal and no change-log row. On both servers, the generic write tools (odoo_create, odoo_write, odoo_archive, odoo_execute, and odoo_unlink where enabled) therefore refuse to:
    • create a knowledge.article whose parent is in the workspace; or
    • call any method other than reads on a knowledge.article that is in the workspace, including the workspace root.
    An article is in the workspace if its parent_path starts with the root article's. The error names the context tools as the way to make the change. The two context write tools are the only path past the guard. The guard does not apply in the Knowledge app.
  • Existing controls unchanged. No-delete and no-model-tampering stay on. Nothing is archived or deleted by the tools. Every call is recorded in the existing MCP activity log.
  • Data classification. Articles hold internal ledger structure (ids, codes, journal set-up), not counterparty deal terms. Anything more confidential stays out of the workspace.

Independent server parity

The independent server (odoo-mcp/server.py, XML-RPC with the user's API key) gets the same four tools. Names, inputs, outputs and behavioural hints must match the module exactly, so a skill drives either server unchanged. The existing parity tests check this: the four tools are not added to MODULE_ONLY.

The logic is the same on both servers. These differences follow from the independent server calling Odoo from outside, as the user, over XML-RPC:

Release follows the repo's standing rule for server.py changes: run the pytest suite, rebuild the Docker image, regenerate the tarball, and package the plugin with build_plugin.py.

Migration and rollout

  1. Maintainer: release the MCP module with the four tools, two groups, the two settings and the write guard. Create the workspace root and its property definition.
  2. QIP (repo): release the independent server with the same four tools and the write guard, and set context_root_article_id in each deployment's odoo_config.json. In Knowledge, give contributors "Can edit" on the Proposals article for users who will propose through the independent server.
  3. QIP finance (through the MCP): create the parent articles and copy the property definition to each. Then import the current 0. Odoo context folder: one article per file, properties filled from each file's front matter (including the three drift properties for entity articles), markdown converted to HTML, and internal links rewritten as article links. Imported articles start as approved with their existing verified-on dates.
  4. QIP finance: confirm the list of companies in scope against res.company; spot-check five articles against the folder; then make the OneDrive folder read-only and add a pointer to Knowledge.
  5. Team: call odoo_context_for at the start of every Odoo task (added to the Odin skill).

Acceptance tests

On staging, with the imported content.

  • odoo_context_for(67, "elimination") returns the Woolwich 1 Elimination entity and rulebook articles, the shc-ii Journals, Chart and Partners articles, and a 31 July year-end warning.
  • odoo_context_for(23) returns the Edinburgh 1 Elimination articles and the sp6 structure articles, and nothing from shc-ii.
  • A structure's child article (e.g. shc-ii → Journals), two levels below the root, is found by its properties. new
  • An article placed under a parent with no property definition is not returned, and odoo_context_for warns that the expected article is missing. new
  • Changing a test company's year end in Odoo makes odoo_context_for return a drift warning, without editing the article. (Odoo 18 requires a subsidiary's year end to match its root's, so the test changes it on the root, which cascades.)
  • odoo_context_for(68) returns a consolidation journal of CJE (224), owner 6, shared: true.
  • odoo_context_for(23) returns a consolidation journal of CJE (122), owner 14, and never 224 or 202. new
  • odoo_context_for(9) lists only B Woolwich Limited's own bank journal(s), never one owned by another company. A company with no bank journal gets an error in that entry.
  • For a user without access to the owning company, that journal entry is an error, not the journal. new
  • A user without workspace access gets no articles from either read tool. odoo_context_for still returns the company facts and journals that the user's Odoo rights allow.
  • A user allowed only into SP6 companies gets no shc-ii or Woolwich articles from odoo_context_lookup, by query or by article_id ("not found"). They do still get Read me first and Organisation. new
  • The same user calling odoo_context_for(67) is refused. new
  • The same user calling odoo_context_propose against a Woolwich article is refused. new
  • odoo_context_lookup with a query returns no proposals unless include_proposals is true. new
  • odoo_context_lookup with both query and article_id, or with neither, is refused. new
  • A contributor with read-only workspace access can call odoo_context_propose. It creates a proposal showing that user as creator, and the target article is unchanged.
  • A user outside the contributor group calling odoo_context_propose is refused. new
  • A contributor calling odoo_context_apply_proposal is refused. A reviewer's approval updates the target, sets verified-on to today and adds one change-log row.
  • A rejected proposal stays active under Proposals → Rejected and does not appear in the Trash. new
  • A write tool pointed at an article outside the workspace, or at any other model, is refused.
  • A reviewer calling odoo_write, odoo_create, odoo_archive or odoo_execute against an article in the workspace is refused on both servers. The same calls on an article outside the workspace still work. new
  • On the independent server, the same calls as the tests above return the same results as on the module, including the company filter and the refusals. new
  • Both servers return identical markdown for the same article. new
  • The server-parity tests pass with the four tools on both servers and matching hints. new
  • The upgraded module installs on staging with Knowledge present, and its existing tests still pass. new
  • odoo_context_for responds in under 3 seconds with all companies' content loaded.
